# ADR-003: 실시간 스트리밍 방식으로 SSE를 선택한 이유

## Overview

K8s 장애 진단 응답은 AI가 분석을 마치는 즉시 한 번에 던져주는 방식이 아니라, 분석 과정을
스트리밍으로 실시간 전달할 필요가 있었습니다. 이를 위한 서버→클라이언트 실시간 통신 방식으로
Server-Sent Events(SSE)와 WebSocket을 비교했습니다.

## Motivation

핵심 이유는 사용자 경험이었습니다. REST API는 응답이 완전히 생성되기 전까지는 아무것도 받아볼
수 없습니다. 반면 AI와 실시간으로 대화하는 것처럼, 생성되는 토큰을 스트림으로 받아 그때그때
화면에 뿌려주는 방식이 실제 AI 채팅 경험에 훨씬 가까웠습니다.

참고로 Spring AI 공식 문서에서는 SSE가 MCP(Model Context Protocol)의 표준 통신 전송 방식으로
언급됩니다. 이 프로젝트는 현재 MCP를 직접 사용하고 있지는 않아 이것이 결정에 직접적인 제약을
준 요인은 아니지만, Spring AI 생태계 전반에서 SSE가 실시간 스트리밍의 관례로 자리잡고 있다는
것을 확인하는 참고 자료가 되었습니다.

## 검토한 대안

### WebSocket

양방향 통신을 지원하는 표준 프로토콜입니다. 클라이언트가 서버로 임의 시점에 메시지를 보낼 수
있어야 하는 요구사항이 있다면 자연스러운 선택입니다. 다만 이번 요구사항은 AI 응답을
서버에서 클라이언트로 실시간 전달하는 단방향 흐름이 핵심이었고, 양방향 통신을 위한 연결
관리(연결 유지, 핸드셰이크, 별도 프로토콜 처리)까지 필요하지는 않았습니다.

### SSE (Server-Sent Events)

HTTP 기반의 단방향(서버→클라이언트) 스트리밍입니다. Spring MVC의 `SseEmitter`로 구현할 수
있으며, 브라우저 표준 스펙상 자동 재연결 기능도 기본으로 제공됩니다.

## 결정

SSE를 선택했습니다. REST API처럼 완성된 응답을 한 번에 받는 방식보다, AI가 생성하는 토큰을
실시간 스트림으로 받아 보여주는 방식이 사용자 경험 측면에서 더 적합하다고 판단했고, 이
요구사항에는 서버→클라이언트 단방향 스트리밍이면 충분해 WebSocket의 양방향 연결 관리
복잡도를 감수할 필요가 없었습니다.

## 결과 / 실제로 겪은 문제

SSE는 WebSocket보다 단순하다는 선택 이유와 별개로, 실제 구현 과정에서는 예상치 못한 문제들을
여러 차례 겪었습니다.

### 1. 브라우저 기본 `EventSource`로는 인증 헤더를 못 보냄

브라우저 표준 `EventSource(url)` API는 HTTP 요청 헤더에 `Authorization: Bearer <JWT>`를
추가할 수 없습니다. 이 때문에 `EventSource`를 포기하고, `fetch()` + `ReadableStreamDefaultReader`

- `TextDecoder`로 청크 스트림을 직접 파싱하는 방식(`data:`, `event:`, `\n\n` 구분자를 수동으로
  분해)으로 SSE 클라이언트를 직접 구현해야 했습니다.

### 2. 스트리밍 도중 예외가 발생하면 프론트 파서가 그대로 깨짐

SSE 스트리밍 도중 백엔드에서 예외(비즈니스 예외, DB 에러 등)가 발생하면, 기존 REST
컨트롤러처럼 일반 JSON(`ResponseEntity`)으로 에러를 반환할 경우 프론트엔드 SSE 파서가 이를
SSE 포맷으로 인식하지 못해 파싱이 깨졌습니다. `GlobalExceptionHandler`에서 SSE 요청 여부
(`isSseRequest()`)를 판별해, 예외 발생 시에도 `SseEmitter`를 통해 `event: error` 포맷으로
감싸 전달하도록 전면 수정했습니다.

### 3. 클라이언트가 창을 닫으면 스택트레이스가 로그에 쏟아짐

사용자가 브라우저 탭을 닫거나 새로고침하면 비동기 SSE 세션이 끊기면서
`AsyncRequestNotUsableException` 스택트레이스가 서버 로그에 대량으로 찍혔습니다. 이는 실제
장애가 아니라 정상적인 클라이언트 이탈 상황이므로, 전역 예외 처리기에서 이 예외를 별도로
캐치해 "비동기 SSE 세션 정리 완료" 로그 한 줄만 남기고 조용히 세션을 종료하도록 수정했습니다.

### 4. URL 쿼리 파라미터로 JWT를 노출하는 보안 문제

`EventSource`의 헤더 제약을 우회하려고 SSE 연결 URL의 쿼리 파라미터에 JWT를 직접 넣는 방식은
`access_token`이 서버 액세스 로그와 브라우저 히스토리에 그대로 남는 보안 취약점을 만들었습니다.
이를 해결하기 위해 단기 발급 SSE 티켓 패턴(`ConsumeSseTicketUseCase`)을 도입해, 1회용
short-lived 티켓을 먼저 발급받은 뒤 그 티켓으로 SSE에 접속하는 구조로 변경했습니다.

## 트레이드오프

**얻은 것**

- REST의 완성 응답 대기 방식이 아니라, AI가 실제로 "타이핑하듯" 응답을 스트리밍하는 사용자
  경험을 구현했다.
- WebSocket 대비 연결 관리 복잡도를 줄였다.
- 표준 HTTP 위에서 동작해 기존 REST 인프라(인증, 로깅 등)와 통합하기 쉬웠다.

**포기한 것 / 겪은 비용**

- "SSE는 간단하다"는 선택 이유와 달리, 브라우저 표준 `EventSource`의 제약(인증 헤더 불가) 때문에
  결국 클라이언트 파서를 직접 구현해야 했다. 표준 스펙만 보고 판단했을 때의 단순함과, 인증이
  필요한 실제 서비스에 적용했을 때의 단순함은 달랐다.
- 예외 처리, 클라이언트 이탈 처리, 인증 방식까지 SSE 전용으로 별도 설계해야 했고, 이는 일반
  REST API를 만들 때는 필요 없던 추가 작업이었다.
