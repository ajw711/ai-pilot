# [Troubleshooting] SSE 스트리밍 중 예외 발생 시 프론트 파서가 깨지는 문제

## 상황

SSE로 AI 응답을 스트리밍하는 도중 백엔드에서 예외(비즈니스 예외, DB 에러 등)가 발생하면,
프론트엔드에서 스트림 파싱이 그대로 깨져버리는 문제가 있었다.

## 원인

일반 REST 컨트롤러에서는 예외가 발생하면 `GlobalExceptionHandler`가 이를 잡아 JSON 형식의
에러 응답(`ResponseEntity`)으로 변환해 반환한다. 그런데 SSE 요청 중에 같은 방식으로 예외가
처리되면, 클라이언트는 여전히 `data: ...` 형식의 SSE 이벤트를 기다리고 있는 상태에서 갑자기
일반 JSON 응답을 받게 된다.

프론트엔드의 SSE 파서(`fetch()` + `ReadableStreamDefaultReader`로 직접 구현한 청크 스트림
파서)는 `data:`, `event:`, `\n\n` 구분자를 기준으로 스트림을 해석하도록 만들어져 있었기
때문에, 이 형식에 맞지 않는 일반 JSON이 들어오면 파싱 자체가 실패했다.

## 해결

`GlobalExceptionHandler`에서 현재 요청이 SSE 요청인지 여부(`isSseRequest()`)를 판별하도록
수정했다. SSE 요청 중 예외가 발생하면, 일반 JSON 응답 대신 `SseEmitter`를 새로 생성해
`event: error` 형식의 SSE 이벤트로 감싸서 반환하도록 변경했다. 이렇게 하면 예외가 발생해도
클라이언트의 SSE 파서가 계속 같은 프로토콜(SSE 이벤트 형식) 안에서 에러를 인식하고 처리할
수 있다.

## 교훈

- 스트리밍 응답과 일반 요청·응답은 예외 처리 전략을 다르게 가져가야 한다. 같은
  `GlobalExceptionHandler`를 쓰더라도, 현재 요청이 어떤 프로토콜/포맷으로 응답을 기대하고
  있는지에 따라 예외 응답의 형식 자체를 분기해야 한다.
- 브라우저 표준 `EventSource`를 쓰지 않고 `fetch()` 기반으로 SSE 파서를 직접 구현한
  경우([SSE 선택 이유](../decisions/003-sse-choice.md) 참고), 파서가 기대하는 포맷에서
  벗어나는 모든 응답이 파싱 실패로 이어질 수 있다는 점을 특히 더 주의해야 한다.
